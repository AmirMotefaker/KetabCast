# v0.2.0-beta.5.1.2 — Gemini TTS Retry Policy v2

## Trigger

Dual-Voice Batch A controlled rerun `31520914385` was dispatched from
`v0.2.0-beta.5.1.1` / `852ab7198698573eeacdcfc36e2324c6d6b95c15`.

The new transient-vs-daily classifier passed, but the first narration chunk
still failed before QA/media creation.

Observed sequence:

1. a first provider/transport attempt was consumed without an HTTP retry log;
2. the second attempt received HTTP 429 with
   `Please retry in 52.787645711s`;
3. the beta.5.1.1 retry loop only allowed two attempts, so the 429-specific
   retry branch was no longer eligible.

No dual-voice media tag or asset was created.

## Retry Policy v2

- maximum three attempts per narration chunk
- global network-request hard cap remains 10
- retryable HTTP statuses:
  - 408
  - 429
  - 500
  - 502
  - 503
  - 504
- explicit per-day quota remains non-retryable until daily reset
- provider RetryInfo / `Please retry in ...s` remains authoritative for 429
- transport/read failures get bounded exponential backoff + jitter
- malformed/provider-response failures get bounded backoff + jitter
- minimum request-start pacing increased from 7s to 12s
- every transient retry path writes explicit evidence to workflow logs
- validate mode self-tests the retry policy

## Product safety

This hotfix does not:

- generate audio
- create or modify the dual-voice media release
- modify `src/content/episodes.json`
- change current Piper playback
- change the 0/10 verified Dual Voice count

Batch A remains tracked by Issue #53 and will be rerun only after this exact
hotfix is released.
