# v0.2.0-beta.5.1.5 — Gemini TTS Audio Response Format Contract

## Trigger

Controlled Batch A run `31570098554` from exact `v0.2.0-beta.5.1.4`
(`2bd4fac6596e993a41428a76ba64e9df21b3f90b`) failed on the first Gemini
generation POST with HTTP 400:

`Audio delivery mode is not supported.`

All downstream QA, artifact and media publication steps were skipped.

## Root cause

The TTS request declared an unsupported explicit delivery mode:

```js
const TTS_RESPONSE_FORMAT = Object.freeze({
  type: "audio",
  delivery: "inline",
});
```

There were two validation contracts tied to that old shape:

1. `validateInteractionPolling()` required `delivery === "inline"`;
2. `validateSelection()` required exactly the keys `delivery` + `type`.

The first publisher attempt corrected the request and Interaction self-test but
stopped later on a Master-doc anchor mismatch. Recovery r2 then correctly
detected that the second `validateSelection()` delivery assertion still existed.
Recovery r3 corrected that second contract before lifecycle continuation.

## Fix

The supported request contract is now:

```js
const TTS_RESPONSE_FORMAT = Object.freeze({
  type: "audio",
});
```

Both deterministic validators require a type-only response format and explicitly
reject a `delivery` property.

Preserved unchanged:

- Interaction ID completion polling
- audio data / URI extraction
- no duplicate generation POST after accepted Interaction ID
- Retry Policy v2
- 12-second request pacing
- generation POST hard cap 10
- media publication hardening

## Safety

This hotfix does not generate TTS.

Unchanged:
- `.github/workflows/dual-voice-production.yml`
- `src/content/episodes.json`
- Piper production audio
- player behavior
- Dual Voice progress remains 0/10

`media-dual-v0.2.0-beta.6` must remain absent.
