# v0.2.0-beta.5.1.4 — Gemini TTS Interaction Completion Polling

## Trigger

Controlled Batch A run `31565336801` was dispatched from exact source
`v0.2.0-beta.5.1.3` / `3b10a6fc133ca02611c95a60f1be6bf64a4ae9ed`.

The workflow passed both repository self-tests:

- transient-vs-daily quota classifier
- Retry Policy v2

Generation then failed on the first Atomic Habits / Sulafat chunk.

Observed sequence:

1. generation POST #1 returned HTTP success in about 1.3 seconds but no inline
   audio was present;
2. generation POST #2 returned HTTP success in about 1.8 seconds but no inline
   audio was present;
3. the renderer treated both successful responses as provider failures and
   submitted duplicate generation POSTs;
4. generation POST #3 then received HTTP 429 with
   `Please retry in 7.083135772s`.

No QA, recovery artifact, media tag, media release, or media asset was created.

## Diagnosis

This milestone treats the following as an inference, not as direct proof from
the failed run because the old logger intentionally did not print provider
response bodies after HTTP success:

The two very fast HTTP-success responses were likely accepted Interaction
resources that did not yet contain final inline audio, or returned audio by URI.
The renderer incorrectly assumed every successful POST must already contain
audio bytes.

Google's current Interactions API exposes an Interaction resource with an `id`,
a status such as `in_progress` / `completed` / terminal states, and a
`GET /v1beta/interactions/{id}` retrieval endpoint. Audio content can contain
inline `data` or a `uri`. Audio response format also supports explicit
`delivery: "inline"`.

Primary documentation:
- https://ai.google.dev/gemini-api/docs/speech-generation
- https://ai.google.dev/api/interactions-api-v1
- https://ai.google.dev/gemini-api/docs/interactions-breaking-changes-may-2026

## Interaction completion contract

The renderer now:

- explicitly requests `response_format: { type: "audio", delivery: "inline" }`;
- recognizes both inline audio data and audio URI blocks;
- on HTTP-success with an Interaction ID but no audio, reuses the same ID and
  polls `GET /v1beta/interactions/{id}`;
- never starts a duplicate generation POST while an accepted Interaction ID is
  still pending;
- polls every 5 seconds for up to 15 minutes;
- retries transient GET 408/429/5xx with existing Retry-After/backoff policy;
- keeps the generation POST hard cap at 10;
- keeps `networkRequestsUsed` as the compatibility field for generation POSTs;
- records GET polling separately as `interactionPollRequests`;
- treats `completed` without audio and terminal Interaction states as explicit
  failures with a safe summary;
- logs only interaction ID/status/step-types/content-types/audio-presence;
  prompt text and base64 audio are never written to diagnostic logs;
- can download an HTTPS audio URI as a fallback, while only sending the API key
  to Google API hosts.

## Deterministic validation

Validate mode self-tests:

1. queued/in-progress interactions are pending;
2. completed nested inline audio is extracted;
3. completed nested audio URI is recognized;
4. terminal statuses are classified;
5. inline delivery is required;
6. safe diagnostics do not contain audio payload bytes;
7. accepted interactions do not trigger duplicate generation POST behavior.

Expected marker:

`Dual-voice interaction-polling PASS: queued/in_progress reuse ID; completed audio extraction; inline delivery; no duplicate generation POST.`
