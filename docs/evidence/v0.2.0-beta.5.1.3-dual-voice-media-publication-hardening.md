# v0.2.0-beta.5.1.3 — Dual-Voice Media Publication Hardening

## Context

Retry Policy v2 (`v0.2.0-beta.5.1.2`) is fully finalized at exact SHA
`f98c1e3b7b8824e9777925321b7199cfc4842a1e`.

Before consuming Gemini TTS quota again, the dual-voice production workflow was
reviewed and a publication-risk was found in the media upload step.

The workflow previously used:

```bash
gh release upload "$MEDIA_TAG" \
  "$FILE#$ASSET_NAME" \
  --clobber=false
```

The subsequent verification queried GitHub by `.assets[].name == "$ASSET_NAME"`.

This is unsafe because `file#label` may assign a display label without changing
the actual uploaded asset filename. If the local podcast basename differs from
the desired canonical asset name, generation and QA can succeed and publication
can still fail after expensive TTS usage.

The workflow also uploaded its recovery artifact only after media publication.
That meant a media-upload failure could leave no downloadable workflow artifact
containing the already-generated audio.

## Hardening

The workflow now:

1. uploads the `.dual-voice` evidence/recovery artifact immediately after the
   safety gate and before creating/uploading the media release;
2. creates a canonical temporary upload path:
   `$RUNNER_TEMP/dual-voice-release-assets/$ASSET_NAME`;
3. copies the podcast file to that canonical path;
4. verifies the copied upload file has the same SHA-256 and byte count as the
   manifest source;
5. uploads the canonical path with:
   `gh release upload "$MEDIA_TAG" "$UPLOAD_FILE"`;
6. keeps the existing pre-existing-asset refusal;
7. keeps GitHub digest, size and public download-back SHA/byte verification;
8. removes the ambiguous `file#label` and `--clobber=false` invocation.
