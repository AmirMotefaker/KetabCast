# v0.2.0-beta.5.1.9 — Gemini TTS long completed-audio materialization window

## Trigger

Controlled Batch A run `31597210578` used exact source:

- tag: `v0.2.0-beta.5.1.8`
- SHA: `87da6953fcc3977266eaf5cb2674f4fcdf12d639`

The run passed repository validation, Gemini secret validation, the
completed/no-audio deterministic tests, and the content_blocked recovery tests.

Production TTS then reached:

- `atomic-habits/female/Sulafat: TTS 1/2`
- `atomic-habits/female/Sulafat: TTS 2/2`
- `atomic-habits/male/Schedar: TTS 1/2`

The Schedar generation POST was accepted. Its Interaction reported
`status=completed`, but the initial response and six same-ID GET polls contained
no audio data, no audio URI, and no model-output steps. The old local grace window
therefore failed closed after about 30 seconds with
`TTS_INTERACTION_COMPLETED_WITHOUT_AUDIO`.

No QA, evidence artifact, immutable media tag/release, or production-player
promotion occurred in that failed run.

## Production timing evidence

The same run shows that the two successful Sulafat chunk generations took
approximately 3 minutes 22 seconds and 5 minutes 15 seconds before the next chunk
started. A fixed ~30-second completed/no-audio grace is therefore materially shorter
than observed production TTS generation times.

This does not prove Google guarantees delayed audio materialization after
`status=completed`; the Interactions documentation describes `completed` as a
terminal status. The longer same-ID window is an empirical Preview-model safeguard
that avoids a duplicate generation POST while allowing the already accepted
Interaction more time to expose its audio.

## Fix

- Keep `INTERACTION_POLL_INTERVAL_MS = 5000`.
- Keep `INTERACTION_POLL_TIMEOUT_MS = 15 * 60 * 1000`.
- Derive completed/no-audio poll bound from those existing values:
  `15m / 5s = 180 same-ID GET polls`.
- Never issue another generation POST after an Interaction ID is accepted.
- Interaction GET polling remains separate from generation POST accounting.
- Generation POST hard cap remains 10.
- content_blocked recovery POST hard budget remains 2.
- response format remains `{ type: "audio" }`.
- transcript, voice selection, safety settings, workflow, episode metadata, player,
  and Piper production audio are unchanged.

## Deterministic runtime validation

Success case intentionally exceeds the previous bound:

`completed/no-audio -> same-ID GET x11 without audio -> GET x12 returns audio`

Assertions:

- exactly 12 same-ID GET calls;
- exactly 12 materialization sleeps;
- Interaction ID is unchanged;
- resolved audio is valid;
- no generation POST is involved in materialization polling.

Fail-closed case:

`completed/no-audio -> same-ID GET x180 without audio -> TTS_INTERACTION_COMPLETED_WITHOUT_AUDIO`

Assertions:

- exactly 180 GET calls;
- exactly 180 materialization sleeps;
- failure reports `materializationPolls=180`.

## Provider documentation

Gemini Interactions defines `completed` as a terminal status and TTS examples normally
read audio from the completed interaction. Gemini 3.1 Flash TTS Preview also supports
streaming audio generation. This hotfix deliberately keeps the already working
non-streaming production transport and only widens the bounded same-ID materialization
window to minimize blast radius.

Official references:

- https://ai.google.dev/api/interactions-api
- https://ai.google.dev/gemini-api/docs/speech-generation
