# v0.2.0-beta.5.1.10 — Batch A resilience

## Trigger

Controlled Batch A run `31601664847` used exact source
`v0.2.0-beta.5.1.9 / e52eea22bb10b50fb5add1ddd921e7b13da47805`.

The run passed all deterministic materialization and content-blocked tests.
Production then generated both Atomic Habits Sulafat chunks. Schedar chunk 1
returned `content_blocked`; the first recovery POST received transient HTTP 429,
the second recovery POST later returned `content_blocked`, and the strict
two-recovery-POST budget failed closed.

No evidence artifact, QA, immutable media tag/release, or product promotion was
created.

## Provider guidance

Google documents 429 as a retryable rate-limit condition and recommends backoff.
Gemini TTS documentation also documents prompt-classifier false rejections and
recommends explicit speech-synthesis framing.

Official references:

- https://ai.google.dev/gemini-api/docs/api-errors
- https://ai.google.dev/gemini-api/docs/troubleshooting
- https://ai.google.dev/gemini-api/docs/speech-generation

## Fix

### Smaller controlled sub-runs

Batch A gains:

- `batch-a-atomic` — Atomic Habits only
- `batch-a-deep-work` — Deep Work only

Each sub-run has 1 book x 2 voices x 2 chunks = 4 planned successful generation
POSTs. The overall per-run network hard cap remains 10.

### Separate transient network attempts from classifier outcomes

- per-chunk attempts: max 5
- recovery-prompt network POST cap: max 4
- actual recovery POSTs still consume the overall network hard cap
- recovery `429/408/5xx` remains transient/retryable
- recovery `content_blocked` increments a separate classifier-block counter
- classifier-block cap: max 2
- a second classifier rejection fails closed
- recovery remains available only when the exact transcript SHA already
  synthesized successfully earlier in the same process
- `prohibited_content` remains fail-closed and is never treated as this observed
  `content_blocked` false-rejection path

Deterministic production-like test:

`primary content_blocked -> recovery 429 -> recovery content_blocked -> recovery audio`

must PASS without exceeding the network hard cap.

### Failure checkpoint

If generation fails, GitHub Actions uploads the current `.dual-voice` directory as
a 14-day artifact named
`dual-voice-failed-<subbatch>-<run_id>`.

This checkpoint is evidence only in this milestone; it does not auto-promote partial
audio and does not create the immutable media tag.
