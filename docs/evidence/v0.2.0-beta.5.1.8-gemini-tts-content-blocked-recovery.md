# v0.2.0-beta.5.1.8 — Gemini TTS content_blocked classifier recovery

## Trigger

Controlled Batch A run `31587048578` used exact source
`v0.2.0-beta.5.1.7` / `30c75a04ca29a22c77e7c58b45832b74555991aa`.

Materialization runtime tests passed. Production generation then progressed through:

- `atomic-habits/female/Sulafat: TTS 1/2`
- `atomic-habits/female/Sulafat: TTS 2/2`
- `atomic-habits/male/Schedar: TTS 1/2`

The Schedar request failed with HTTP 400 `content_blocked`.

The same Atomic Habits chunk had already synthesized successfully with Sulafat in the
same workflow run. This makes a TTS prompt-classifier false rejection a strong
explanation; it does not prove that every future content_blocked response is benign.

No evidence artifact, immutable media tag/release, or product/player mutation was
created by the failed run.

## Fix

- Primary director prompt now starts with an explicit speech-synthesis request.
- Spoken transcript is enclosed by explicit START/END markers.
- A second, more explicit classifier-recovery framing preserves the transcript exactly.
- No transcript wording is changed, removed, encoded, or obfuscated.
- No safety setting is added, lowered, or disabled.
- Recovery is allowed only when the exact transcript chunk SHA-256 has already
  synthesized successfully earlier in the same process.
- At most one alternate-framing recovery is attempted for a blocked chunk.
- Global content-blocked recovery budget is 2 actual POST attempts.
- The recovery counter increments immediately before every network fetch that uses
  the recovery prompt, including generic transport/408/429/5xx retry attempts.
- A third recovery POST is refused before its network request.
- Generation hard cap remains 10 POSTs.
- Other HTTP 400 responses remain non-retryable.
- `prohibited_content` is not classified as this narrow recovery condition.

## Deterministic runtime validation

The self-test executes the real `callTts()` loop with injected network dependencies.

Positive:
`prior same-text success -> 400 content_blocked -> alternate framing -> 2xx audio`

Fail closed:
`unseen transcript -> 400 content_blocked -> no recovery -> TTS_CONTENT_BLOCKED_NO_SAFE_RECOVERY`

Actual recovery POST budget:
`primary content_blocked -> recovery POST #1 gets retryable 500 -> recovery POST #2 gets retryable 500`
consumes the complete global recovery budget. A later eligible primary request may
still be sent, but after it returns `content_blocked`, the third recovery POST is
refused before network fetch with
`TTS_CONTENT_BLOCKED_RECOVERY_BUDGET_EXHAUSTED`.

The deterministic test asserts that only two recovery-prompt POST bodies are ever sent
across those calls while the overall generation hard cap remains 10.

## Safety

This hotfix does not dispatch Batch A and does not create or modify
`media-dual-v0.2.0-beta.6`. Production Piper episode metadata/player remain unchanged.
